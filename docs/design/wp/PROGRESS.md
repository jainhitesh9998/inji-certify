## Findings about the existing test suite ("trust but verify")

- Status-list assignment cannot run on H2: `StatusListCredentialService.initializeAvailableIndices` uses a native PostgreSQL `generate_series` insert, so every existing test of the feature mocks the service and no test issues a credential with a real status entry. Covered since P1-10a by `StatusListPostgresTest` (Testcontainers). The H2 `schema.sql` now has the three status tables; an end-to-end status golden needs the Testcontainers PostgreSQL context from P0-05.
- Status list credentials were signed with `Ed25519Signature2020` under the VC 2.0 context alone, which defines `DataIntegrityProof` only: the proof `type` expanded to an undefined term, so strict verifiers rejected every list (danubetech accepted them because signer and verifier drop the same triple). Fixed in P1-10a for `Ed25519Signature2020` (suite context added); `Ed25519Signature2018` lists (compose `certify-mock-mdl.properties`) keep the defect because the context loader serves no `ed25519-2018` context. The same applies to any VC 2.0 template signed with a legacy suite whose context the template omits; output validation on the new surface should reject such documents.
- `POST /credentials/status` takes the bare status list id in `credentialStatus.statusListCredential` (and `id`), while the credential carries the list URL; a caller that forwards the credential's own `credentialStatus` gets `STATUS_LIST_NOT_FOUND`. Kept as is on the compatibility surface; the `StatusProvider.update` path (P5) should accept the URL.
- The Flyway chain creates `key_policy_def` but carries none of its rows; they come from `db_scripts/inji_certify/dml` through `init_db.sh`. A database prepared by Flyway alone cannot start the keymanager (`initKeys` needs the policies). `StatusListPostgresTest` seeds the CSV itself; a DML migration (`INSERT ... ON CONFLICT DO NOTHING`) needs a decision because it would also run on baselined databases.
- `application-test.properties` sets `mosip.certify.status-list.vc-sign-algo`, a key nothing reads; the service reads `mosip.certify.status-list.signature-crypto-suite`.
- 0.14.0 findings from the draft-13 recording (`P0-02-notes.md`): its mDoc `validityInfo` lacks `signed` (ISO/IEC 18013-5 9.1.2.4) and wraps the credential as a Document with a tagged `issuerAuth`; an unknown metadata version answers HTTP 200 with the MOSIP `errors[]` envelope; its H2 test schema predates its own `CredentialConfig` entity, so no 0.14.0 test inserted a configuration through the repository; the token response and access token carry `c_nonce`, which develop dropped without a replacement on the token side.
- On H2 a `TEXT[]` column read back as one stringified element is re-stringified on every write, so `cryptographic_binding_methods_supported` of the mDoc configuration deepens (`[[[cose_key]]]`) with every test that touches the row; the depth depends on test order (the first P1-12 slice was red on CI for this while green locally). `Goldens.collapseBrackets` folds any depth to one pair. On PostgreSQL the column is a real array and the bug does not occur.
- `Goldens.normalize` sorted object arrays by their raw string before sorting keys, so a recorded golden did not re-normalise to itself; fixed (key-sorted comparison). Only array order in the v1 `did.json` and `jwks.json` goldens changed.
- `StaticContextLoaderTest.maxEntries_full_expiredEntriesPurged_allowsNewInsert` was flaky: a 1 ms cache TTL raced the loader's constructor preload, so the entry sometimes expired before the first load and `resourceLoader.getResource` was invoked twice (`TooManyActualInvocations`). It slipped one merge through (P1-06) because the local gate reads the suite summary after the run; the test now uses a 200 ms TTL and a 400 ms wait (full suite 892/892 after the change). A `Clock` injected into `StaticContextLoader` would make it fully deterministic.

## Spec and behaviour findings from the goldens (to fix in the adapters, not silently)

- `W3CJsonLD.addProof` derives the proof's `created` by parsing the credential's `issuanceDate`/`validFrom` (a `Z` timestamp) with `LocalDateTime.parse(...).atZone(ZoneId.systemDefault())`, so on a JVM outside UTC `created` is shifted by the local offset (5:30 h on IST). The `ldp_vc` formatter reads the timestamp as UTC; the legacy path keeps the shift until the adapter switch (zero wire change).
- The claim-169 CWT carries `kid` but no `x5chain`: `Credential.signQRData` asks keymanager with `protectedHeader {x5c: true, kid: true}` but keymanager's `CoseHeaderBuilder` only honours its own keys, so the certificate is never included and a verifier must resolve the key from `jwks.json` by `kid`. Keymanager also adds `exp`, `nbf` and `iat` with its own defaults. The `CwtEnvelope` route should include the chain and take the validity from configuration.
- `did.json` lists the DID itself in `assertionMethod` and `authentication` instead of verification-method ids (DID Core §5.3.1 expects references to verification methods); `alsoKnownAs` and `service` are emitted as empty arrays. Verifiers that resolve `verificationMethod` directly still work, which is why the credentials verify.
- `EcdsaSecp256r1Signature2019` (P-256, `proofValue` base58btc) is Certify's own suite name: it is not in the W3C LD cryptosuite registry and no library outside Certify verifies it (danubetech has k1 and Ed25519 only). Spec-correct P-256 issuance is `ecdsa-rdfc-2019` (Data Integrity), which Certify already supports; the legacy suite should be deprecated on the compatibility surface.
- `POST /pre-authorized-data` answers HTTP 200 with `{"errors":[{"errorCode":"unknown_claims"}]}` (legacy `ResponseWrapper` envelope) instead of an OAuth-style 4xx; the new `/oid4vci` surface must not inherit this.
- The credential offer's `credential_issuer` is `mosip.certify.identifier` (with servlet path) while the issuer metadata's `credential_issuer` is `mosip.certify.domain.url`; OpenID4VCI requires the same Credential Issuer Identifier in both (second face of the dual-identity finding above).
- The access token's `sub` is the offer's claims map serialized as JSON in `HashMap` order (PII inside the token, nondeterministic), `client_id` is the empty string, and `aud` is built by string concatenation (`${mosip.certify.identifier}/v1/certify/issuance/credential`), which duplicates the servlet path whenever the identifier already carries it (as in the test profile).
- Issuer metadata orders `credential_metadata.claims` by `HashMap` iteration, so the document differs between JVM runs; the order should follow the configured display order.
- Optional display fields absent from a configuration are serialized as `null` (`logo`, `background_color`, `background_image`, `text_color`, `claims[].display`); OpenID4VCI defines them as optional objects and strings, so they should be omitted (`@JsonInclude(NON_NULL)` on `MetaDataDisplayDTO` and `CredentialMetadataDTO.Claims`).
- `mosip.certify.identifier` (proof audience, SD-JWT `iss`) and `mosip.certify.domain.url` (`credential_issuer` in metadata) are two keys for one identity; in the test profile they already disagree (`.../v1/certify` vs `http://localhost:8090`). See docs/design/14-configuration.md.
- `credential_definition.type` is emitted sorted alphabetically (`["GoldenCredential","VerifiableCredential"]`) because the mapper stores types as a sorted comma list; the issuer's configured order is lost.
- On H2, `TEXT[]` columns come back as one stringified element (`"[did:jwk, did:web]"`); PostgreSQL returns a proper array. One more reason the repository tests must run on PostgreSQL (P0-05).

- `CertifyApplicationTests.test()` boots the application a second time by calling `CertifyServiceApplication.main()` inside a `@SpringBootTest`; it asserts only that the class is not null.
- Controller tests are `@WebMvcTest` with mocked services; no test exercises an end-to-end issuance through the real signing path.
- Repository tests run on H2 with `schema.sql`, not on the PostgreSQL DDL under `db_scripts` (JSONB, `TEXT[]`, enum and partial indexes are never exercised).
