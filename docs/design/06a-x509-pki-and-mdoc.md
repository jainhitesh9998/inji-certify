# PKI-based issuance: X.509 chains, mDoc/mDL, and issuers without keymanager

> Part of the Inji Certify extensibility design. Baseline: `develop` at `a1cfd63` (1.0.0-beta.1-SNAPSHOT). Index: [README.md](./README.md).

mDoc/mDL and SD-JWT VC with `x5c` are trusted through certificate chains, not DID documents. Today Certify can attach a chain only through keymanager's CSR-and-upload flow, puts only the leaf certificate into an mDoc, validates no certificate profile, and cannot sign with a key and certificate an issuer already holds in its own PKI. A separate `x509` provider family, a per-format `CertificateChainPolicy` and trust-anchor publication make these formats first class, with keymanager or without it.

What each format needs from the signer:

| Format | Trust model | The signature must carry | Certificate profile | Rotation |
| --- | --- | --- | --- | --- |
| `mso_mdoc` (ISO/IEC 18013-5) | Issuing Authority CA (IACA) root per issuer; a Document Signer Certificate (DSC) signs each MSO; verifiers hold IACA certificates from a VICAL or bilaterally | COSE\_Sign1 with `x5chain` (header label 33) holding the DSC and any intermediates; ES256 in practice | Annex B: DSC with extended key usage `1.0.18013.5.1.2`, key usage `digitalSignature`, issuer country, a short validity (Annex B caps DS certificate lifetime; confirm the figure for the edition you target), IACA with a CRL distribution point | DSCs rotate often, IACA rarely; overlapping DSCs must both verify |
| `dc+sd-jwt` (SD-JWT VC) | `x5c` chain to a trust anchor the verifier knows, or `iss` plus `/.well-known/jwt-vc-issuer` JWKS | JWS header `x5c` (leaf first) and `iss`; the leaf's SAN (dNSName or URI) must match `iss` | Web PKI or a private PKI; `kid` optional when `x5c` is present | CA policy |
| `ldp_vc`, `jwt_vc_json` | DID document or JWKS; optionally `did:x509` or `x5c` on the verification method | `verificationMethod` URL | none | DID document update |

Where it is patchy today:

| Gap | Evidence | Effect |
| --- | --- | --- |
| An mDoc carries only the leaf certificate | `MDocProcessor.signMSO` (`:512`) sets the unprotected header `includeCertificate=true`; nothing adds intermediates or the IACA, and no `x5chain` policy exists | A verifier that does not already hold the DSC cannot build a path |
| No DSC profile anywhere | `MDocConfig` holds digest algorithm, MSO version and validity years, nothing about certificates; a keymanager-generated signing certificate is signed by the application master key, not by an IACA | Credentials look like mDocs but fail ISO trust validation; AGENTS.md calls mDoc "mock only" |
| Bring-your-own key is impossible | Every key is generated by keymanager (`generateMasterKey`, `generateECSignKey`); the CSR flow (`/system-info/generate-csr`, `uploadCertificate`) lets an external CA sign a keymanager-generated key, but an HSM-resident DSC managed by a national PKI, or a KMS key, cannot be used | Issuers with an existing PKI must move keys into keymanager |
| Rotation and PKI do not compose | Keymanager rotation creates a new key whose certificate is signed by the master key; each DSC renewal is a manual CSR, external signing and upload cycle; nothing tracks DSC expiry against the Annex B cap | Expired or master-signed DSCs in production |
| SD-JWT `x5c` depends on `ca_cert_store` | Keymanager's `jwsSignV2` builds `x5c` from `getCertificateTrustChain`, which needs the CA certificates uploaded; Certify never checks the leaf SAN against `iss` | A chain that verifiers cannot match to the issuer |
| No trust-anchor publication | Nothing publishes IACA certificates (VICAL) or the SD-JWT trust anchor; `/.well-known/jwt-vc-issuer` is absent | Verifiers configure trust by hand |
| No independent verification in tests | mDoc IssuerAuth and `x5c` chains are not verified by a library Certify did not write | Regressions go unnoticed |

The design, on top of the `KeyProvider` and `Signer` contracts:

```java
// certify-signing
public record SigningKey(KeyRef ref, PublicKeyDescriptor publicKey, CertificateChain chain, Object providerHandle) {}
public record CertificateChain(List<X509Certificate> leafFirst) {
    Optional<X509Certificate> leaf();  Optional<X509Certificate> root();  List<String> subjectAltNames();
}

public interface CertificateChainPolicy {              // one per format, run at config save (dry run) and before sign
    String formatId();
    void validate(SigningKey key, CredentialConfiguration cfg) throws ChainPolicyViolation;
}
// MdocDscPolicy: EKU 1.0.18013.5.1.2, digitalSignature, ES256, validity inside the Annex B cap, IACA present in the chain
// SdJwtX5cPolicy: leaf first, SAN matches iss, chain terminates at a known trust anchor
// NonePolicy: ldp_vc and jwt_vc

public record CoseHeaderPolicy(X5Chain x5chain /* FULL | LEAF | NONE */, boolean kid) {}
public record JwsHeaderPolicy(X5c x5c /* FULL | LEAF | NONE */, KidStrategy kid, String typ, boolean x5tS256) {}

// certify-keyprovider-x509-*: keys and chains an issuer already has, no keymanager tables
// x509-file:   PKCS#12 or PEM key with the full chain (also the CLI and test provider)
// x509-pkcs11: HSM-resident key, chain from PEM files
// x509-kms:    KMS key, chain from PEM files

public interface TrustAnchorRegistry {                  // Certify-owned trust_anchor table or files
    List<X509Certificate> anchors(String purpose);      // "mdoc-iaca", "sd-jwt", "mdoc-reader"
}
```

- Every `SigningKey` carries its chain. The keymanager provider fills it from `getCertificateChain` (so keymanager users keep the CSR-and-upload flow and gain full chains in mDoc and correct `x5c` ordering); the `x509` providers fill it from the operator's files.
- Header policy is data per configuration with format defaults: mDoc `x5chain=FULL`, SD-JWT `x5c=FULL` with `typ: dc+sd-jwt`, W3C formats `NONE`. The envelope builders apply it identically for every provider.
- `CertificateChainPolicy` runs when a configuration is saved (`/v2/credential-configurations` dry run) and before every signature, so an expired DSC or a chain without an IACA is refused with a named reason instead of producing an unverifiable credential. Keymanager-issued certificates go through the same policy, which is what turns "mock mDoc" into a real one.
- `TrustAnchorRegistry` and `KeyPublisher` publish what verifiers need: IACA certificates as a VICAL-style list and per-certificate download, `/.well-known/jwt-vc-issuer` with the issuer JWKS for SD-JWT VC, the root of the `x5c` chain for download. Trust anchors used for verification inside Certify (reader authentication, presentation during issuance) come from the same registry.
- Rotation for DSCs: a `KeyRef` may name a version; `publicKeys()` returns overlapping DSCs; a Micrometer gauge `certify.signing.key.expires_in_days{keyRef}` and a startup warning cover the Annex B window; the CLI adds `certify keys csr`, `certify keys import-chain` and `certify keys check` for operators who do not use keymanager, while keymanager users keep `/system-info/generate-csr` and `uploadCertificate`.
- Tests verify with independent code: mDoc IssuerAuth and chain validation with an ISO 18013-5 library, SD-JWT `x5c` validation with a standard JOSE library, both fed by the `x509-file` provider and checked-in test IACA and DSC certificates.

Where this lands: Phase 1 puts `CertificateChain` on `SigningKey` and the header policies into the envelope builders, with the keymanager provider returning full chains (mDoc stops being leaf-only without any configuration change); Phase 3 adds `certify-keyprovider-x509-file` (PKCS#12 or PEM with the full chain, plus a `dev` mode that generates a key and a test IACA-to-DSC chain at startup so a developer needs no keymanager and no HSM), `CertificateChainPolicy` for mDoc and SD-JWT, and the trust-anchor registry, so the conformance runs use a real DSC chain; Phase 4 makes `mso_mdoc` non-mock end to end with IACA publication and the PKCS#11 and KMS `x509` variants; Phase 5 adds the CLI key commands. None of it requires the keymanager tables when an `x509` provider is chosen, as set out in the database section.
