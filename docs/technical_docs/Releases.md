# Changes in the extensibility rebuild (unreleased, `design/extensibility`)

## Draft-13 endpoints restored and deprecated

The OpenID4VCI draft-13 credential endpoints of release 0.14.0 are served again by the `oid4vci-d13` adapter (on by default, `certify.protocol.oid4vci-d13.enabled`): the 0.14.0 body on `POST /issuance/credential`, `POST /issuance/vd12/credential` and `POST /issuance/vd11/credential`. They are deprecated from this release: every answer carries `Deprecation` and `Link` headers, calls are counted in `certify.deprecated.calls{endpoint=oid4vci-d13-credential|oid4vci-d13-versioned-credential}`, and `mosip.certify.deprecated.<endpoint>.enabled=false` answers `410 Gone`. Replacement: `POST /oid4vci/credential` (OpenID4VCI 1.0). Removal no earlier than two minor releases after this one.

## Notification endpoint on the new surface

`POST /oid4vci/credential` answers with a `notification_id` and the issuer metadata under `/oid4vci` advertises `notification_endpoint`: wallets report `credential_accepted`, `credential_failure` or `credential_deleted` to `POST /oid4vci/notification` (OpenID4VCI 1.0 section 10) with the access token of the issuance. Every issuance through the new surface is recorded in the `issuance_transaction` table created by the 1.1.0 migration and purged after `certify.protocol.oid4vci-v1.notification.retention` (default one day). The compatibility endpoints are unchanged.

## v2 configuration API

`POST`, `GET`, `PUT` and `DELETE /v2/credential-configurations` take and return the configuration model the rebuilt core reads (`formatConfig`, `signing`, `template`, `issuanceStrategy`, `status`, `display`, `protocol`), version templates in `credential_template`, and dry-run a body that carries `sampleClaims` through the template engine and formatter before saving it (`400 template_render_failed` otherwise). `POST /v2/credential-configurations/{id}/preview` renders a saved configuration against given claims without signing. Rows written through v2 carry every v1 column too, so `/credential-configurations` (v1), the compatibility endpoints and the issuer metadata see them unchanged. The v1 API is unchanged and not yet deprecated.

## Single-use nonces and batch issuance on the new surface

A `c_nonce` from `POST /oid4vci/nonce` now authorises one credential request: after the credentials are issued the nonce is dropped, and a replayed proof answers `400 invalid_nonce` (`certify.protocol.oid4vci-v1.nonce.single-use=false` restores the previous behaviour). The issuer metadata under `/oid4vci` advertises `batch_credential_issuance.batch_size` (`certify.protocol.oid4vci-v1.batch.size`, default 10); a request whose `proofs` exceed it answers `400 invalid_credential_request`. The compatibility endpoints and the draft-13 endpoints are unchanged.

## Path-based tenants

`certify.tenancy.resolver=path` serves each configured tenant under `{domain}{servletPath}/t/{tenant}/oid4vci/...` with `.../t/{tenant}/oid4vci` as its Credential Issuer Identifier, next to the host resolver. Unconfigured path tenants answer as the default tenant. A tenant may also set `certify.tenancy.tenants.<id>.display` and `.authorization-servers` for its metadata document; token validation still uses the deployment's authorization server.

## Tenant DID documents

With `certify.tenancy` enabled, a tenant configured with `issuer-did` issues under that DID (the proof's `verificationMethod` is `<tenant did>#<kid>`) and `GET /.well-known/did.json` on the tenant's host publishes the deployment's keys under the tenant's DID, so a verifier resolves the tenant's credentials from the tenant's own document. Single-tenant deployments are unchanged.

## Compatibility credential endpoint deprecated

`POST /issuance/credential` with the 1.0.0-beta.1 body (`credential_configuration_id`, `proofs`) keeps working and is deprecated from this release: every answer carries `Deprecation` and `Link` headers, calls are counted in `certify.deprecated.calls{endpoint=oid4vci-v1-compat-credential}`, and `mosip.certify.deprecated.oid4vci-v1-compat-credential.enabled=false` answers `410 Gone`. Replacement: `POST /oid4vci/credential` (OpenID4VCI 1.0, advertised by `GET /oid4vci/.well-known/openid-credential-issuer`). `POST /nonce` stays. Removal no earlier than two minor releases after this one, never in a patch.

## Pre-authorized offers may name a subject

`POST /pre-authorized-data` accepts an optional `subject` next to `claims`: the identifier the data provider resolves (for the CSV plugin, the row id). It becomes the access token's `sub`, so plugins that look the record up by `sub` work in the pre-authorized code flow without eSignet. Offers with `claims` behave as before.

## Offers on the `/oid4vci` surface

`POST /pre-authorized-data` accepts an optional `issuer` (`oid4vci` or `legacy`, case-insensitive, blank means absent; absent, `certify.protocol.oid4vci-v1.offers.default-issuer`, `legacy` unless set) and an optional `offer_by_value`. An `oid4vci` offer names the `/oid4vci` identifier in `credential_issuer`, and the access token its code is exchanged for is addressed to that surface's credential endpoint, so the wallet can redeem it at `POST /oid4vci/credential` without the deployment adding an audience. `offer_by_value: true` returns the offer document as `credential_offer` next to the `openid-credential-offer://` deep link (which then carries the offer, URL-encoded per RFC 3986, instead of a pointer). The `/oid4vci` metadata document now publishes the issuer `display`, and both metadata documents publish `mso_mdoc` signing algorithms from one COSE map. The offer page gains a surface selector, defaults to `/oid4vci` for `mso_mdoc`, returns offers by value, and decodes and shows an `mso_mdoc` credential's IssuerSigned elements and portrait. Behaviour without `issuer`, `offer_by_value` and an `mso_mdoc` configuration is unchanged.

Tenant binding is a property of the `/oid4vci` surface only. A `legacy` offer is tenant-agnostic, exactly as before: its code is redeemed wherever a token is requested and it mints the deployment's configured audience. An `oid4vci` offer created under a non-default tenant (path tenants, `certify.tenancy.resolver=path`) names that tenant's identifier and addresses its token to that tenant's credential endpoint, and a token bound to one tenant is accepted only at that tenant's surface. Two limits are worth stating plainly: `/pre-authorized-data` and `/oauth/token` are served on the deployment's own paths only — the authorization server metadata publishes one token endpoint — so completing an offer created for a non-default tenant needs tenant-aware authorization-server and offer endpoints, which Certify does not provide yet; and a tenant that configures no `issuer-identifier` shares the default `/oid4vci` identifier, and therefore its audience.

`/.well-known/oauth-authorization-server` grows `pre-authorized_grant_anonymous_access_supported` (OID4VCI 1.0 section 12.3) only when the deployment opts in: `certify.as.pre-authorized-grant.advertise-anonymous-access=true`, client attestation is not required, and `grant_types_supported` lists the pre-authorized code grant. The default is off, so an unchanged deployment's authorization server metadata is byte-identical to before.

## Credential issuer metadata ignores `Accept`; authorization server metadata lists only completable grants

`GET /oid4vci/.well-known/openid-credential-issuer` (and its path-tenant and root-mapped forms) answers the unsigned OpenID4VCI 1.0 section 12.2.2 document with `Content-Type: application/json` for every `Accept` value, including `application/jwt` (signed metadata is not supported) and `text/html`. It no longer answers 406 through content negotiation. The deprecated draft-13 metadata paths (`GET /issuance/.well-known/openid-credential-issuer` and `GET /.well-known/openid-credential-issuer?version=...`) answer the same way; the `/issuance/.well-known/openid-credential-issuer` alias used to answer 500 to those two values. The DID document alias is not metadata and keeps its mapping. Bodies are unchanged, so the recorded goldens replay byte for byte.

`/.well-known/oauth-authorization-server` now advertises only grants the server can complete, and only when the document describes Certify's own token endpoint: exactly Certify's identity (`mosip.certify.identifier` or `mosip.certify.domain.url`, comma lists allowed) followed by the context path and servlet path as Spring Boot mounted them (`server.servlet.context-path`, `spring.mvc.servlet.path`; `/` is the empty prefix, a trailing slash is dropped) and `/oauth/token`. `mosip.certify.authorization.url` and `mosip.certify.oauth.issuer` do not make an endpoint Certify's own, so any other authorization server - eSignet's `.../v1/esignet/oauth/token`, or an external server at a Certify-like path such as `https://idp.example/v1/certify/oauth/token` - is served exactly as configured, as before. A token endpoint on Certify's own origin that is not that URL is also served as configured and logged once at WARN. The comparison is textual: host case and an explicit default port (`:443`, `:80`) must be written the same way in the token endpoint and the identity, otherwise the document is served as configured and the WARN names the mismatch. As RFC 8414 section 2 requires, `authorization_code` is dropped unless a `certify.as.clients` client is registered (Certify then advertises `authorization_endpoint` and PAR) or `mosip.certify.oauth.interactive-authorization-endpoint` is configured; the configured grant list is trimmed; `code_challenge_methods_supported` is published only with that grant; `grant_types_supported` is never left empty (it becomes the pre-authorized code grant); and `interactive_authorization_endpoint` and `require_interactive_authorization_request` are written together, only with the endpoint. Keeping `authorization_code` when the IAE is configured is a compatibility interpretation, not strict RFC 8414 conformance: the IAE is an earlier revision of the OpenID4VCI 1.1 editor's draft and OpenID4VCI 1.0 final has no such endpoint, so a wallet that insists on `authorization_endpoint` whenever the grant is listed still refuses that document. The visible changes are Certify-own-endpoint only: a deployment with no client and no IAE loses `authorization_code` and `code_challenge_methods_supported`; one that listed only `authorization_code` becomes pre-authorized only (`pre-authorized_grant_anonymous_access_supported` still follows the configured list, so it does not appear there); one with no IAE loses `require_interactive_authorization_request`. The document of a deployment that configures the IAE - including develop's compose stack with the rebuild overlay, where `certify-default.properties` sets it - is byte-identical, and so is develop's plain compose document, whose token endpoint is on the authorization server's host and is therefore not Certify's own. External authorization server metadata (eSignet) is repeated exactly as before. The mDL demo stack is pre-authorized only: one grant, no `authorization_endpoint`, PAR or IAE.

Reading a credential configuration no longer writes it. Every load of an `mso_mdoc` row in a read-write transaction used to rewrite the whole `credential_config` row, because Hibernate saw `mso_mdoc_claims` as changed on every load (the snapshot copy of the JSON column turned each nested claim into a plain map): once per metadata read, per v1 `GET /credential-configurations/{id}`, and per request that looked a configuration up and then ran any read-write transaction. On PostgreSQL the row was rewritten with the values just read, so documents did not change, but a read could overwrite an admin update committed in between; on the H2 test schema it also nested the array columns. The column is now mapped with a JSON type whose copies (load snapshot, merge, second-level cache) keep the declared type (`TypedJsonBinaryType`; the stored bytes are unchanged) and the read paths of `CredentialConfigurationServiceImpl` are read-only transactions; with `spring.jpa.open-in-view` on, a configuration loaded by one of them stays read-only for the rest of that request. No wire change.

Outside the scope of F-17 but changed by it: the deprecated `GET /.well-known/openid-credential-issuer?version=...` mapping (`D13DiscoveryController`) no longer declares `produces = application/json`; it sets the same `Content-Type` on the response, so it answers `application/json` for any `Accept` like the other metadata paths. Its body is unchanged and the draft-13 goldens replay.

## Compatibility metadata: `mso_mdoc` signing algorithms

Two changes are visible on the compatibility surface's `/.well-known/openid-credential-issuer`. An `mso_mdoc` configuration whose signing algorithm has no COSE identifier no longer fails the whole metadata document: the value is dropped with a warning (previously an `IllegalArgumentException` answered the request with an error), so the document still advertises everything else, and the configuration is better fixed by choosing ES256, ES384, ES512 or EdDSA. And an ES384 or ES512 configuration now publishes the COSE identifiers -35 and -36, where it previously failed the document for lack of a mapping. ES256, EdDSA, ES256K and RS256 rows are byte-identical to before.

## Token Status List

A configuration whose `status.mechanism` is `TokenStatusList` gives its SD-JWT VC payload or mDoc MSO a `status.status_list` entry (draft-ietf-oauth-status-list); the lists are signed JWTs (`typ statuslist+jwt`) under `certify.status.token-status-list.key-ref`, served at `GET /credentials/token-status-list/{id}` as `application/statuslist+jwt`, and re-signed by the status-list batch job on revocation. Bitstring Status List for `ldp_vc` is unchanged.

## Status-list batch job: oldest first, failing lists held back

The batch job that publishes revocations (`StatusListUpdateBatchJob`, every list kind) now applies each list's pending transactions strictly in the order they were committed and never lets one list hold up the others. Each run reads the oldest pending transactions that name a list, ordered by `transaction_log_id` (the database sequence; `cr_dtimes` is the writing node's clock and no longer orders anything), at most `mosip.certify.batch.status-list-update.batch-size`; a list whose update fails is excluded from the rest of the run in the query itself, so none of its newer transactions can be applied before an older one that failed, and its pending rows cannot fill the window other lists need. A row without a status list id is no longer read (it never could be applied). A JWT Token Status List or Bitstring list that fails is tried again on the next run, as before.

A CWT Status List Token list (`mso_mdoc`, M-11) is held back by what its failure is. A transient one — the key provider or HSM cannot resolve or sign, the IACA's CRL is stale (`CRL_STALE`), a certificate is not yet valid — is tried again on the next run, then after `certify.status.token-status-list.batch.retry-backoff` (default `PT1M`), doubled per consecutive failure up to `certify.status.token-status-list.batch.retry-backoff-max` (default `PT15M`). A permanent one — the Document Signer is revoked or its reference now names another certificate, the signer is not issued by a configured IACA or not for this purpose, the stored list does not verify with its pinned signer — is quarantined for `certify.status.token-status-list.batch.quarantine` (default `PT1H`) and tried again after it, or at the next run as soon as the IACA trust material (an anchor or its CRL) changes; no restart is needed after an operator's fix. The transactions of a held list stay pending and are applied in order once it can be signed. Every run logs a WARN naming the quarantined lists and their pending transactions, and the gauges `certify.status.batch.quarantined-lists` and `certify.status.batch.quarantined-transactions` (Prometheus `certify_status_batch_quarantined_lists`, `certify_status_batch_quarantined_transactions`) count them; a refusal is logged without a stack trace. Holds are kept in memory per instance. No schema change.

Each list is then applied in one database transaction that locks the list's row, reads its pending transactions again, applies them and marks them processed, so a run that resumes after another instance applied its selection (one paused past ShedLock's lease) applies nothing stale. A status change (`POST /credentials/status`, the VC-API status endpoint) takes the same row lock before it queues its transaction, so a list's transactions are numbered in the order they commit; a status change for a list waits while the job signs that list. `mosip.certify.batch.status-list-update.lock-at-most-for` now defaults to `10m` (was `50m`); a deployment that sets it keeps its value.

A status change whose `statusListIndex` is not on its list (negative, or at or past the list's size) is refused with `requested_index_is_out_of_bounds_for_status_list_capacity` before anything is queued: VC-API answers `400`, `/credentials/status` the usual error wrapper, as for an unknown list. Such a transaction already in the queue is closed by the job without being applied — an ERROR names it, and the counter `certify.status.batch.rejected-transactions` (Prometheus `certify_status_batch_rejected_transactions_total`) counts it — and the list's other transactions are applied in the same run. It used to hold a Token Status List back for ever, and an index of 2^35 or more could set another credential's bit on a JWT or CWT list.

`certify.status.token-status-list.size-bits` must be a positive multiple of 8 and at most 8,388,608 (2^23) for JWT lists too, the ceiling the CWT codec reads back; a value outside it now refuses startup instead of creating a list whose bit array is truncated to whole bytes.

Marking a JWT Token Status List `FULL` when its indices run out writes `credential_status` alone: it used to save the row it had read, which reverted a revocation the batch job committed in between. The served bytes do not change.

## X.509 chains for SD-JWT VC and mDoc

The `x509-file` provider's dev mode now signs generated keys with a dev CA (`certify.keyprovider.x509-file.ca-alias`, default `dev-ca`) instead of self-signing them, a configuration may choose how much of the chain its SD-JWT `x5c` and mDoc `x5chain` carry (`signing.x5c` in the v2 configuration API: `full`, `leaf`, `without-anchor`, `none`), and the chain is checked (validity, links) before an SD-JWT VC or mDoc is signed. Configurations without the setting are unchanged.

## DPoP-bound access tokens

`POST /oauth/token` accepts a `DPoP` proof (RFC 9449) on every grant and then issues a sender-constrained token (`cnf.jkt`, `token_type: DPoP`) that the credential endpoints already enforce; the authorization server metadata advertises `dpop_signing_alg_values_supported`. Without a proof the token is a Bearer token, as before.

## Attestation-based client authentication

With attesters configured under `certify.as.client-attestation.attesters.<id>.jwks`, `POST /oauth/par` and `POST /oauth/token` validate the `OAuth-Client-Attestation` and `OAuth-Client-Attestation-PoP` headers (draft-ietf-oauth-attestation-based-client-auth) and the authorization server metadata advertises `token_endpoint_auth_methods_supported: ["attest_jwt_client_auth"]`; `certify.as.client-attestation.required=true` refuses unauthenticated calls, as HAIP requires. Without attesters nothing changes.

## Authorization code flow in Certify's own authorization server

Once a client is registered under `certify.as.clients.<client-id>.redirect-uris`, the authorization server metadata advertises `authorization_endpoint`, `pushed_authorization_request_endpoint` and `require_pushed_authorization_requests`, and wallets run the authorization code flow with pushed requests and PKCE (`S256`) against `POST /oauth/par`, `GET /oauth/authorize` and `POST /oauth/token`. The subject of an authorization comes from `certify.as.authorization.subject-mode`: `none` (default) refuses, `fixed` approves every request for `certify.as.authorization.fixed-subject` without user interaction, which is meant for conformance runs and demos only. Deployments without registered clients see no change.

## Holder keys as `did:key` with RSA

A proof whose `kid` is an RSA `did:key` (multicodec `0x1205`) was decoded by 1.0.0-beta.1 but never verified: the resolver built the key without its `kid`, so signature verification found no matching key and the request failed with `invalid_proof`. It verifies now on both surfaces. Every other holder key form (`jwk` header with P-256, Ed25519 or RSA; `kid` as `did:jwk` or `did:key` with Ed25519, P-256 or secp256k1) is unchanged and covered by `HolderDidMethodsTest`; see `docs/design/18-compatibility-validation.md`.

## Key attestations on the new surface

`POST /oid4vci/credential` validates a `key_attestation` JOSE header on `jwt` proofs and accepts the `attestation` proof type (OpenID4VCI 1.0 Appendix D and F): the attestation must be typed `key-attestation+jwt`, signed by an attester configured under `certify.protocol.oid4vci-v1.key-attestation.attesters.<id>` (`jwks`, or `trust-anchor` for an `x5c` chain), unexpired, and carry the proof key in `attested_keys`; a configuration that lists `key_attestations_required` under `proof_types_supported.jwt` refuses proofs without one and checks the accepted `key_storage` and `user_authentication` values. One credential is issued per attested key, within `batch_size`. Compatibility surfaces are unchanged (`attestation` proofs answer `unsupported_proof_type` there, as any unknown type did).

## `did:web` holder keys, and `did:key` in the advertised default

A proof whose `kid` is a `did:web` DID URL is resolved by fetching the DID document over HTTPS when `certify.protocol.oid4vci-v1.did-web-holders.enabled=true` (`timeout` per fetch, default 5 s); the verification method named by the `kid` supplies the key as `publicKeyJwk` or `publicKeyMultibase`, and the credential is bound to the `kid`. Off by default, so nothing changes for deployments that do not set it. The local profile's `cryptographic-binding-methods-supported` default now lists `did:jwk` and `did:key` for `ldp_vc` and `dc+sd-jwt`, the methods the issuer resolves without configuration (the compose profile already did); a deployment that enables `did:web` holders adds `did:web` to its own default or per configuration.

## P-256 keys with a leading zero byte

The DID document encoded the P-256 `publicKeyMultibase` from a minimal-length X coordinate, so for about one key in 256 (an X starting with a zero byte) `did.json` published a wrong point and no verifier could check credentials signed with that key; the `did:key` holder resolver built JWK coordinates the same way, changing the thumbprint of such holder keys. Both are fixed-width now. A deployment whose P-256 signing key is affected publishes the right key after upgrading, without a key change.

## VC-API issuer endpoints

With `certify.protocol.vc-api.enabled=true`, `POST /vc-api/credentials/issue` (W3C VCALM, the CCG VC-API) takes `{credential, options}` from a client registered under `certify.protocol.vc-api.clients.<id>` (HTTP Basic with the client id and `secret`; `credential-configurations` optionally limits what it may issue), signs the body with the `ldp_vc` configuration of `issuanceStrategy: SUPPLIED` whose `@context` and `type` match, and answers `201 {verifiableCredential}`; refusals are `application/problem+json`. `POST /vc-api/credentials/status` updates a status list entry named in the request or found through the ledger by `credentialId`. Today's `POST /credentials/status` is unchanged; nothing is served under `/vc-api` unless enabled.

## Four defects found by the workflow run

The v1 and v2 configuration APIs evicted the `issuerMetadataCache` through `@CacheEvict`, which fails with "Cannot find cache" on a deployment whose `mosip.certify.cache.names` does not list that name (every deployment upgrading with its own list); the eviction is programmatic and tolerant now, and the name is still worth adding to the list so metadata is cached. The service jar lacked `certify-keyprovider-jca`, which the x509-file provider needs, because the service declared it with test scope; enabling `certify.keyprovider.x509-file` failed at startup with `ClassNotFoundException`. The compose stack's `certify_init.sql` created `status_list_credential.capacity` where the DDL and the entity say `capacity_in_kb` (renamed in 0.13.0), so status lists failed on a fresh compose stack. And once a Token Status List existed, a Bitstring credential issued afterwards was given an index on that JWT list because the Bitstring lookup ignored the list type; the lookup is type-aware now. All four fixed.

## Offer page

With `certify.offer-page.enabled=true`, `{servletPath}/offer/` serves a page that creates a pre-authorized credential offer for a chosen configuration and subject, shows the `openid-credential-offer://` deep link as a QR code for a wallet, and can run the pre-authorized code flow itself (token, `c_nonce`, a proof signed in the browser, the credential). Off by default.

## Metadata location for the `/oid4vci` surface

OpenID4VCI 1.0 (section 12.2.2) forms the metadata URL of a Credential Issuer Identifier with a path by inserting `/.well-known/openid-credential-issuer` between host and path, so the new surface's document must also be reachable at `https://<host>/.well-known/openid-credential-issuer/v1/certify/oid4vci` (and `.../v1/certify/t/<tenant>/oid4vci` for path tenants). Certify keeps serving it under the servlet path; the compose stack's nginx maps the inserted form, and a deployment's proxy must do the same (`docs/design/15-deployment.md`).

## Proof `iss` in the pre-authorized code flow

A `jwt` proof presented with a token from the anonymous pre-authorized code flow may carry `iss` equal to the holder's own DID (the `did:jwk` of the proof key, or its `kid` without the fragment), which Inji Wallet sends to issuers with a nonce endpoint; OpenID4VCI 1.0 asks wallets to omit `iss` there, and the value names nothing the signature does not prove. A client_id, when known, must still match `iss`; any other value is still refused. The compose stack's seeded `FarmerCredential` now advertises EdDSA next to RS256, PS256 and ES256, as the deployment default does, so Inji Wallet's Ed25519 proofs are accepted there.

## mDoc output from the refactored formatter follows ISO/IEC 18013-5

The refactored `mso_mdoc` formatter (`certify-format-mdoc`, decision D1 of `docs/design/20-mdl-issuer.md`) serves `/oid4vci`, the draft-13 endpoints (`/issuance/credential` with the 0.14.0 body, `/issuance/vd12/credential`, `/issuance/vd11/credential`) and, only when `certify.protocol.oid4vci-v1.compat-core.enabled=true`, the compatibility endpoint `POST /issuance/credential`. Credentials from those paths change on the wire as listed below. With `compat-core` off (the default), `POST /issuance/credential` still runs the legacy `utils.MDocProcessor`, and its mDoc output is unchanged (the `legacy-develop` golden).

- `validityInfo` timestamps are `tdate` (`#6.0`) strings with whole seconds only (`2026-11-13T10:15:30Z`), never fractional seconds (9.1.2.4).
- `digestID`s are random distinct unsigned integers in `0..2^31-1` per namespace; the template's `digestID` values are ignored (9.1.2.5). Verifiers must look items up by the identifier they carry, not by position.
- The IssuerAuth `x5chain` carries the document signer certificate and its intermediates, never the self-signed IACA (HAIP); a configuration whose key has no certificate chain, or with `signing.x5c` `none` (also refused at save on the v2 API), or `leaf` with intermediates, now fails with `certificate_chain_invalid` instead of issuing an mDoc without `x5chain`.
- Element values are typed by ISO/IEC 18013-5 Table 5 for namespace `org.iso.18013.5.1` (`portrait` and the biometric templates are `bstr` from base64, `birth_date` `#6.1004`, `issue_date`/`expiry_date` `full-date` or `tdate`, `driving_privileges` an array of maps, `age_over_NN` `bool`, `sex`/`height`/`weight` `uint`) and by `formatConfig.elementTypes` elsewhere; untyped namespaces keep the `YYYY-MM-DD` heuristic, but only inside element values (identifiers, namespace names and `docType` stay text), and integers beyond 64 bits stay CBOR integers (bignums) instead of text.
- The MSO's default validity is 90 days (`certify.format.mdoc.mso-validity`, a `Duration`, at least one minute) instead of two years, capped at the document signer certificate's `notAfter` and at an mDL's `expiry_date`. When `mso-validity` is not set, `certify.format.mdoc.validity-period-years` and then the 1.0.0-beta.1 key `mosip.certify.mdoc.validity-period-years` apply, in that order; likewise `certify.format.mdoc.digest-algorithm` falls back to `mosip.certify.mdoc.digest-algorithm`, then `SHA-256`. The formatter logs once at startup which key decided each value. A deployment that set neither validity key gets 90 days on these paths where the legacy service gave two years. An mDL whose `expiry_date` has passed, or is today, is refused.
- For the `org.iso.18013.5.1.mDL` doctype the document is validated before signing (`mdoc_data_model_invalid`): every mandatory Table 5 element, `issuing_country` equal to the document signer certificate's country, `un_distinguishing_sign` 1-3 upper-case letters, and a JPEG-only `portrait` (complete, at most 1 MiB and 4096x4096 pixels, decodable without errors); JPEG 2000 portraits are no longer accepted.
- The device key is taken from the proof's `did:jwk`, `did:key` or JWK as P-256/P-384/P-521 (EC2) or Ed25519 (OKP) without an `alg` label; a holder key the MSO cannot carry (another curve, EC coordinates shorter than the field width, a point off the curve, an Ed25519 key that is not a valid point) is answered `400 invalid_proof` instead of `500`.

Changes on those paths that can make a configuration that issued before now fail (check them before switching on `compat-core` or moving wallets to `/oid4vci` or draft-13):

- The template's `docType` must equal the configuration's `doctype`; a mismatch is a template error instead of an mDoc whose MSO names another document type (G7).
- The configured `digestAlgorithm` is now actually used to compute the digests (G5): a deployment that set `SHA-384` or `SHA-512` previously issued SHA-256 digests labelled with that algorithm, and now issues digests of that algorithm.
- Text-typed Table 5 elements refuse JSON numbers: a numeric `document_number` (or `family_name`, `issuing_authority`, ...) in the template is `mdoc_data_model_invalid`; quote it.
- `issuing_jurisdiction` must be an ISO 3166-2 subdivision of `issuing_country`; `nationality` and `resident_country` ISO 3166-1 alpha-2 codes; `sex` an ISO/IEC 5218 code (0, 1, 2 or 9); `issue_date` before `expiry_date`; `issue_date` and `birth_date` not after the issuance date.
- Startup fails unless `certify.format.mdoc.mso-version` is `1.0` and the configured validity is positive (`mso-validity` at least one minute, either `validity-period-years` above zero).
- A "complete JPEG" `portrait` ends with its EOI marker (`FF D9`) as the last two bytes, so padding or metadata appended after EOI is refused; and it must decode with the JDK JPEG reader, which reads YCbCr and greyscale JPEGs only, so a CMYK or YCCK portrait is refused.
- A signing key whose certificate is self-signed (a plain dev key with no CA) is refused with `certificate_chain_invalid`: an ISO/IEC 18013-5 Annex B document signer is issued by an IACA. Keymanager keys (signed by the keymanager root) and `x509-file` dev keys (signed by the dev CA) are not affected.

## Annex B keys in the `x509-file` provider

The `x509-file` provider can generate an ISO/IEC 18013-5 Annex B IACA and Document Signers in dev mode (`certify.keyprovider.x509-file.iaca`, `keys[].profile: mdoc-dsc`), import a Document Signer key and `[DSC, IACA]` chain from PEM files (`pem-keys`), and rotate keys as `alias@version` entries; the gauge `certify.signing.key.expires_in_days{keyRef}` and a WARN 30 days ahead report every current signing certificate, keymanager's included (`docs/design/20-mdl-issuer.md` M-05). The provider is new in the rebuild (P3-01) and has never been part of a release, so no released deployment is affected. A configuration written for an earlier rebuild build changes in two ways only: every alias the provider is given (`keys[].alias`, `pem-keys[].alias`, `iaca.alias`, `ca-alias`) must be lower case and contain at most one `@` (`name` or `name@version`), checked when the properties are bound, so startup fails naming the property instead of a key going missing in a PKCS#12 store that lower-cases aliases; and a Document Signer (a certificate carrying the mDL extended key usage `1.0.18013.5.1.2`) held as a single unversioned entry in an existing keystore no longer resolves once it has expired or before it is valid, because every verifier rejects an mDL signed outside its Document Signer's validity; a plain key with a single entry still resolves whatever its dates, as before.

## mDoc Document Signer policy and IACA publication

An issuer can name the ISO/IEC 18013-5 IACAs its mDoc Document Signers chain to (`certify.pki.trust-anchors.mdoc-iaca[].{id, certificate, crl}`, PEM or DER; the `x509-file` provider's IACAs are added automatically), and can publish them (`docs/design/20-mdl-issuer.md` M-06 and M-08). Nothing changes for a deployment that configures neither: no IACA means the policy below is not enforced (the service logs that once at startup), mDocs are signed exactly as before, keymanager chains stay the certificate alone, and nothing is published.

- **Once at least one IACA is configured, or the `x509-file` provider holds one, every `mso_mdoc` signature on every surface (`/oid4vci`, the draft-13 endpoints, the compatibility endpoint through the core) is checked against them and refused with `certificate_chain_invalid` naming the rule** when the Document Signer was issued by none of them (`DSC_NO_TRUSTED_IACA`; this is the case for keymanager's own certificates, signed by its root), when the signing instant lies outside the DSC's validity (`DSC_NOT_YET_VALID`, `DSC_EXPIRED`) or the IACA's (`IACA_NOT_YET_VALID`, `IACA_EXPIRED`), when the DSC or the IACA breaks its Annex B profile (the `certify-pki` rule, such as `DS_EKU_MISSING`), or when the IACA's CRL lists the DSC (`DSC_REVOKED`). A deployment that adds an IACA while it still signs mDocs with keymanager keys must move those configurations to a DSC the IACA issued: the keymanager CSR flow (`/system-info/generate-csr`, the IACA signs it, `uploadCertificate`) or an `x509-file` key. The v2 configuration API's dry run and `POST /v2/credential-configurations/{id}/preview` run the same check and answer `400 template_render_failed` with the rule.
- A keymanager certificate that a configured IACA issued (the CSR flow) is resolved for signing with that IACA as `[DSC, IACA]`, so the policy can check it; the IssuerAuth still carries the DSC alone (`without-anchor`), and the JWKS `x5c` and DID documents still publish the DSC alone, as before: an IACA is a trust anchor, published at `/mdoc/iaca`, never in the JWKS.
- **Signing under an IACA whose CRL is stale is refused.** Once a configured anchor's CRL is past its `nextUpdate` by more than `certify.pki.stale-crl-grace` (a duration, default `PT24H`; `PT0S` refuses as soon as `nextUpdate` passes), every `mso_mdoc` signature, dry run and preview under that IACA is refused with `certificate_chain_invalid` `CRL_STALE`, because verifiers reject an mDL whose IACA CRL is stale (RFC 5280 6.3.3); within the grace signing continues, the revocations the CRL lists still apply, and a WARN is logged on every refresh. A CRL more than the grace past its `nextUpdate` at startup does not stop the service: it is logged at ERROR, every other credential format keeps issuing, and `mso_mdoc` signing under that IACA is refused (`CRL_STALE`) until a new CRL is in place. The gauge `certify.pki.crl.next_update{anchor}` (base unit seconds; exported to Prometheus as `certify_pki_crl_next_update_seconds{anchor}`) counts down the seconds to each CRL's `nextUpdate` (negative once past) for alerting, for example `certify_pki_crl_next_update_seconds < 86400`. Publish the next CRL well before `nextUpdate`.
- Startup fails when a configured IACA does not meet the Annex B IACA profile, when a configured CRL is not a valid CRL of its IACA, when two anchors share an id, or when an IACA's CRL distribution point is `…/mdoc/iaca/<x>.crl` and `<x>` is not its anchor id (configured or derived; the advertised URL would answer 404) or not a valid id (lower-case letters, digits, `.`, `_`, `-`, at most 64 characters). CRL files are re-read when they change (`certify.pki.trust-anchors.crl-refresh-interval`, default five minutes); a changed file is used only when it validates and moves forward, with a larger cRLNumber and a `thisUpdate` no more than five minutes (the clock skew the CRL profile allows) earlier than the current CRL's. A file that does not validate, or that goes back (an older CRL could un-revoke a Document Signer), is logged at ERROR on every refresh and the current CRL stays in use; the same CRL written again changes nothing. In `x509-file` dev mode the service issues an empty CRL for the dev IACA, valid for `certify.pki.trust-anchors.dev-crl-validity` (seven days) and re-issued half way; its cRLNumber is kept in `<keystore>.crl-numbers` next to the `x509-file` keystore, so numbers keep increasing across restarts and clock changes; the keystore's directory must therefore be writable in dev mode, or the service does not start (the error names that file). With `crl-refresh-interval` zero or negative nothing is re-read or re-issued (the service logs that once at startup): a dev CRL then goes stale after seven days and mDoc signing stops one grace period later, until a restart.
- `certify.pki.publication.enabled=true` serves, without authentication and read-only, `GET /mdoc/iaca` (a JSON list of `{id, subject, country, sha256, notBefore, notAfter, pem, der, crl}`, the downloads as references relative to the list's URL) and `GET /mdoc/iaca/{id}.pem` (`application/x-pem-file`), `.der` (`application/pkix-cert`) and `.crl` (`application/pkix-crl`, DER, cached until its nextUpdate and at most an hour; `404` when the IACA has no CRL). An IACA's id is `certify.pki.trust-anchors.mdoc-iaca[].id`, else the `<id>` of its own CRL distribution point `…/mdoc/iaca/<id>.crl`, else its subject key identifier in hex, so the distribution point to write into an IACA is `https://<host>/v1/certify/mdoc/iaca/<id>.crl`. The compose nginx passes `GET`/`HEAD` under `/v1/certify/mdoc/iaca` from the public host and refuses every other method, and refuses a `;` or `%3b` in the path of any public request (a path parameter nginx and Spring would read differently; the query string may carry one).

## Fixes found while deploying the mDL issuer (F-10)

- Token Status List freshness. A list JWT carries `exp = iat + 2 ttl` and `sub` = its URI, but was signed only when a status changed, so a list nobody revoked anything on expired after two hours and every verifier refused it, and a list signed before `mosip.certify.domain.url` changed kept the old URI in `sub` (draft-ietf-oauth-status-list 5.1 and 8.3 require `sub` to equal the `uri` in the referenced token). `GET /credentials/token-status-list/{id}` now signs the list again before serving it when `exp` is less than `ttl` away, has passed, or `sub` is not the list's current URI: same bits, new `iat`/`exp`, current `sub`. The new JWT replaces the stored one only if that one is unchanged (compare-and-set on `vc_document`), so a re-sign never undoes a revocation the batch job wrote meanwhile; one request per list re-signs at a time and concurrent readers get the previous list while it is still valid. An expired list is never served, not even one just signed again by a signer so slow that the new `exp` passed before it answered (that counts as a failed re-sign): a list that is merely due for renewal is served as stored if signing fails (judged at the moment it is returned, so a list that expires while the signer fails is not served), and an expired one is answered `503` with `Retry-After`. Two settings bound what a slow or failing signer (an HSM or keymanager stall) can cost: `certify.status.token-status-list.renew-wait` (default `PT5S`) is how long a request for an expired list waits for the request that is signing it before it is answered `503`, so a hung signer holds one request thread per list rather than all of them; `certify.status.token-status-list.renew-backoff` (default `PT30S`) is how long after a failed re-sign the list is not signed again (the stored list is served while valid, `503` with `Retry-After` the rest of the window otherwise; the failure is logged once with its stack trace). No schema change. The Bitstring Status List path does not have the expiry problem (its credential carries `validFrom` and no `validUntil`), but its `id` still names the domain at creation time; re-signing it would change the 1.0.0-beta.1 bytes, so it is unchanged.

  Changing `mosip.certify.domain.url` after credentials were issued: the status-list URIs inside those credentials keep the old domain. Keep the old host routed to Certify for as long as they are valid, or reissue them. For Token Status Lists routing alone is not enough: the list is signed with `sub` under the current domain and a verifier compares it with the token's `uri` (draft-ietf-oauth-status-list 8.3), so SD-JWT VC and mDoc credentials issued under the old domain need reissuing.

- BouncyCastle 1.69 plugins. A deployment that loads the published plugin jars (`mock-certify-plugin`, `mosip-identity-certify-plugin` from `injistackdev/inji-certify-with-plugins`) on `loader.path` gets their unshaded BouncyCastle 1.69 ahead of the service's 1.78.1, and the PKI code failed startup with `NoSuchMethodError: SubjectPublicKeyInfo.getPublicKeyData()`. Certify's code now links against any BouncyCastle from 1.69 to 1.78.1; nothing to configure. What CI checks: the `certify-pki`, `certify-signing`, `certify-keyprovider-jca`, `certify-keyprovider-x509-file` and `certify-format-mdoc` tests run on 1.69 (Maven profile `bc169`), and `docs/design/tools/check-bc169-linkage.sh` resolves against 1.69 every BouncyCastle class, method and field referenced by `certify-service`, the Certify modules and the third-party jars on its runtime classpath. Two third-party references do not resolve and are allowed with their reason (`docs/design/tools/bc169-linkage-allowlist.txt`): OkHttp's optional BouncyCastle JSSE platform, used only when `bctls` is installed, and kernel-keymanager's COSE verification of EC signatures (`CoseSignatureServiceImpl`), which Certify never calls; keymanager's own `POST /coseVerify1` and `/cwtVerify` endpoints fail with HTTP 500 for an EC key under 1.69. Those endpoints are among the keymanager controllers its component scan maps inside Certify, as in earlier releases (`/sign`, `/signV2`, `/signRawData`, `/jwsSign`, `/jwtSign`, `/jwtVerify`, `/validate`, `/pdf/sign`, `/coseSign1`, `/coseVerify1`, `/cwtSign`, `/cwtVerify`, `/encrypt`, `/decrypt`, `/encryptWithPin`, `/decryptWithPin`, `/jwtEncrypt`, `/jwtDecrypt`, `/generateArgon2Hash`); they are protected by Spring Security and keymanager's role checks and, on the public host, by the nginx allow-list (being added in M-10b). Behaviour beyond linkage is tested on 1.69 only for those five modules, and plugins' own code is not checked.

- `/oid4vci` issuer metadata. The document under `/oid4vci/.well-known/openid-credential-issuer` no longer carries members whose value is null (`logo`, `background_image`, `background_color`, `text_color`, a claim's `display`): OpenID4VCI 1.0 section 12.2.4 defines them as optional, so they are absent unless configured. `credential_metadata.claims` now follows the configuration's `display.order` (claims it does not list come after, ordered by path) instead of map order. The compatibility documents (`/.well-known/openid-credential-issuer`, `/issuance/...`) are unchanged.

- Issuer metadata after a configuration change. A `PUT /credential-configurations/{id}` (v1 API) is visible again in every issuer metadata document at once (the rebuild had stopped clearing the metadata cache on a v1 update, so the change showed only after the cache expired). Every configuration write, v1 or v2, clears the cache when it is made and again once its transaction has committed.

- v2 configuration API errors. `POST`/`PUT /v2/credential-configurations` now require `scope`, `display.display` and `display.order` (empty lists are allowed) and answer `400 invalid_configuration` naming the missing field; a body without `display.order` used to reach the database and come back as HTTP 200 with the MOSIP error envelope and the SQL statement. Whatever else fails on the v2 API is answered with a 4xx or 5xx status and `{error, error_description}`, without SQL text: a unique-key conflict is `409 configuration_exists`, another database constraint `400 invalid_configuration`, an unreadable body `400`, an unexpected failure `500 server_error`. The v1 API is unchanged.

- Keystores Certify writes. The `x509-file` provider's dev-mode PKCS#12 (and any keystore `JcaKeyProvider.saveAsPkcs12` writes) holds private keys. A new keystore is written to a temporary file in the same directory, created `rw-------` whatever the umask (never readable by other users, not even while it is written), forced to disk and moved into place atomically. An existing keystore is rewritten in place (truncated, written and forced to disk), so it keeps everything the file system attaches to it: owner, group, permissions, macOS ACLs, Linux POSIX ACLs set with `setfacl` and extended attributes; a keystore an operator made `rw-r-----` for a group stays so when dev mode adds a key (one an earlier release left `rw-r--r--` stays so too, with a warning; run `chmod 600` on it). Before each rewrite the previous keystore is saved beside it as `<keystore>.bak` (for example `issuer.p12.bak`), created `rw-------` and replaced atomically on every write: it holds the same private keys, so protect and back it up like the keystore, and restore from it if the service stopped in the middle of a write. When the directory is not writable by the service (or the keystore is bind-mounted as a single file) there is no room for the backup: the keystore is still rewritten in place, without one, and a warning says so. A keystore the service may not write (for example made `0400`, `r--------`) is not touched: the write fails with `AccessDeniedException` (in dev mode the service does not start when it needs to add a key) and no backup is made; make it writable by the service user, or stop dev mode from adding keys. Symbolic links are kept (also chains of links and links reached through a symlinked directory) and the file they name is written; a link loop is refused. On a file system without POSIX permissions a warning asks the operator to restrict a new keystore. Keymanager's own PKCS#12 (`mosip.kernel.keymanager.hsm.config-path`) is created by kernel-keymanager and is unchanged.

- mDL text elements. An `org.iso.18013.5.1.mDL` whose mandatory Table 5 text element (`family_name`, `given_name`, `issuing_authority`, `document_number`, ...) is empty, or is a Velocity reference the template left unrendered because the data source had no value (`$name`, `${name}`, `$!name`, `$!{name}`), is refused before signing with `mdoc_data_model_invalid` naming the element (the v2 dry run and preview report it the same way), instead of being signed with `${family_name}` as the holder's name. Text that merely contains a `$` is issued as before. The legacy `POST /issuance/credential` path with compat-core off is unchanged.

- Service jar name. `mvn package` now writes the executable service jar as `certify-service/target/certify-service.jar` (no version in the file name; the `-javadoc`/`-sources` jars beside it are `certify-service-javadoc.jar`/`certify-service-sources.jar`), and the Dockerfile copies exactly that file. The former `COPY ./target/certify-service-*.jar` matched the javadoc and sources jars too: the classic builder refuses that, and BuildKit copies whichever match sorts last, so a stale jar of another version in `target/` could end up in the image. Repository coordinates (install, deploy) are unchanged; scripts that pick the jar up by its versioned file name should use `certify-service.jar`.

## File data source

A JSON file can serve credential data without a plugin (`docs/design/20-mdl-issuer.md` M-10a, D10): `certify.datasource.file.sources.<id>.path` registers a source whose records are keyed by the access token claim `key-claim` (default `sub`), and a credential configuration selects it with `dataSourceId: <id>`. Fields listed in `binary-fields` name files beside the JSON file; their bytes are read once at startup and reach the template as base64url without padding (an mDoc `bstr`, such as `portrait`). The JSON file may be at most 5 MiB, each binary file 1 MiB and a source 50 MiB in all; links are resolved before the files are checked to lie inside the JSON file's directory; a missing claim or record answers `credential_request_denied`. The id `data-provider-plugin` is reserved. Nothing changes without a source configured; with one, a credential configuration that names no `dataSourceId` still reads from the data-provider plugin, as before. The `MigrateOnly` migration job reads no source.

## `certify-cli pki` and `keys csr|import`

`certify-cli` (`certify-cli/README.md`) handles the ISO/IEC 18013-5 Annex B PKI offline: `pki iaca create` (an IACA key in a PKCS#12 or encrypted PEM file and its self-signed certificate; `--crl-uri` must be `https://<host>/v1/certify/mdoc/iaca/<id>.crl` with an id Certify accepts, or the CLI refuses it, and a URI elsewhere is warned about because Certify will not publish that CRL), `pki dsc issue --csr|--generate` and `pki dsc rotate` (Document Signers and their `[DSC, IACA]` chain, versioned aliases `alias@yyyy-MM[.N]`), `pki crl issue` (CRLs with one revocation inventory per IACA) and `pki check --profile iaca|mdoc-dsc`; `keys csr` writes a PKCS#10 request for a keystore key and `keys import --key --chain [--anchor] [--profile mdoc-dsc]` imports a key and its validated chain (no CA key is ever imported). Existing `keys generate|list|jwks` and `sign` commands are unchanged.

## Compose stack: public-host rules in `certify-nginx`

The compose stack's `certify-nginx.conf` treats a request carrying `CF-Ray` (one that came through the Cloudflare tunnel) as public, and the operator's own calls from the host as local. Public requests reach under `/v1/certify/` only an allow-list of the wallet and verifier surface, by method and normalised path (issuer, authorization server and DID documents, JWKS, offers, status lists, rendering templates by `GET`, the IACA downloads, and the issuance, token, nonce, notification, PAR and offer-minting calls); everything else is 403, including the admin APIs (`system-info`, `credential-configurations` v1 and v2, `credentials/status`, `ledger-search`, `vc-api`, rendering-template writes), actuator, springdoc and the keymanager controllers. A path parameter (`;` or `%3b`) in a public request is 403 before any location is chosen; `/v1/certify/mdoc/iaca` takes `GET` and `HEAD` only. Public `POST /pre-authorized-data` and `/oauth/token` calls are limited to 30 a minute per client (`CF-Connecting-IP`, burst 20, then 429). Local calls are unchanged. These rules live in the compose file only; a Helm or other deployment that exposes Certify publicly needs the equivalent at its own ingress.

## Compose stack: mDL overlay and public overlay

`docker-compose/docker-compose-injistack/docker-compose.mdl.yaml` adds the mDL issuer to the rebuilt compose stack next to the farmer use case (`config/mdl/README.md`): profile `mdl` plus `MDL_PKI_PROFILE` (required) `mdl-dev` (dev-mode Annex B IACA and Document Signer generated into `./data/MDL_PKI`) or `mdl-operator` (the offline `certify-cli` keystore, IACA and CRL mounted read-only from `MDL_PKI_DIR`), `CERTIFY_PUBLIC_URL` as `mosip.certify.domain.url` (default `http://localhost:8091`), the demo holders and portraits through the file data source `mdldemo`, IACA publication on, and a one-shot `mdl-seed` that writes the `org.iso.18013.5.1.mDL` configuration through the v2 API. `docker-compose.public.yaml`, given last, hardens a stack that serves a public host: certify and certify-nginx on 127.0.0.1 only, no PostgreSQL port, the PostgreSQL, keymanager keystore and operator keystore passwords from Compose secrets read through `configtree` (never environment variables), actuator limited to `health`, and a network private to the project; it needs Docker Compose 2.24.4 or later. Neither file changes the base stack when it is not named.
